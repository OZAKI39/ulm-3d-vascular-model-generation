# 二、最重要的转换原则

请特别注意：

**代码中的“调用关系”，在论文中应当转化为“业务流程、功能流程、数据流转过程或系统实现机制”。**

例如，代码中可能是：

```text
Controller
→ Service
→ DataProcessor
→ ModelClient
→ Database
→ Response
```

不要直接写成：

> Controller 调用了 Service，随后 Service 调用了 DataProcessor，之后调用 ModelClient……

这种表达过于接近技术文档。

应当转化为类似：

> 当系统接收到用户提交的请求后，首先对输入信息进行合法性检查和必要的数据整理。在确认请求满足处理条件后，系统将整理后的数据交由核心业务模块进行进一步处理。随后，根据当前任务类型构造模型所需的输入信息，并将其发送至模型服务。模型返回处理结果后，系统对结果进行解析和整理，必要时结合数据库中的相关信息进行补充，最终形成用户可直接使用的响应内容。

也就是说：

**论文应解释“系统为什么这样处理、数据如何流动、每一步解决了什么问题”，而不是机械描述“哪个函数调用哪个函数”。**

# 三、论文写作风格要求

请严格按照硕士学位论文正文的语言风格进行撰写。

必须做到：

1. 使用正式、客观、准确的书面表达。
2. 逻辑严谨，前后内容具有明确的因果关系和递进关系。
3. 每一段都应围绕一个明确的问题展开。
4. 避免口语化、宣传化、夸张化表达。
5. 避免大量使用“显著提升”“极大增强”“高效实现”“先进技术”等空洞评价。
6. 没有数据支撑时，不要自行使用“明显提高”“大幅降低”“显著优化”等结论性语言。
7. 不要为了显得学术而大量堆砌复杂术语。
8. 能用简单、准确的中文解释清楚时，不使用晦涩表达。
9. 专业术语仅在确有必要时使用，并保证上下文能够自然解释其含义。
10. 不要写成产品介绍、项目汇报、软件说明书或系统使用手册。
11. 不要出现大量代码、函数名、类名或参数名。
12. 不要逐文件介绍项目结构。
13. 不要逐行解释源代码。
14. 不要在正文中频繁出现英文类名、变量名、函数名。
15. 不要使用“首先、其次、再次、最后”进行机械堆砌，应根据上下文自然组织逻辑。
16. 不要写出明显具有 AI 生成痕迹的模板化句子。
17. 避免连续出现结构高度相似的段落。
18. 不要一句话重复表达同一个意思。

最终语言效果应当是：

**学术、严谨、清楚，但仍然容易阅读。**

# 四、不要写成技术文档

这是最重要的要求之一。

请主动识别并删除或改写以下“技术文档式表达”。

例如不要大量出现：

```text
系统调用 xxx() 方法
进入 xxx.py 文件
执行 xxxService
通过 xxxController 接收参数
调用 xxx API
函数 A 调用函数 B
方法返回 xxx 对象
变量 xxx 被赋值
```

除非为了说明某个关键实现细节确有必要，否则正文不要直接描述代码名称。

优先改写为：

```text
系统接收用户请求
业务处理模块对数据进行整理
数据经过预处理后进入核心处理阶段
系统根据任务类型构造模型输入
模型服务完成计算后返回结果
结果经过解析和格式化后返回用户
```

论文需要描述的是：

**系统运行机制，而不是源代码本身。**

# 五、从代码工作流中提取“论文逻辑”

请不要简单照搬代码执行顺序。

在正式写作前，请先在内部完成以下转换：

### 第一步：识别代码事实

从当前代码中确定：

* 用户或外部系统从哪里发起请求；
* 系统接收到哪些数据；
* 系统进行了哪些处理；
* 各处理步骤之间有什么依赖关系；
* 哪些步骤属于数据预处理；
* 哪些步骤属于核心业务逻辑；
* 哪些步骤涉及数据库；
* 哪些步骤涉及模型、算法或外部服务；
* 结果如何进一步加工；
* 最终如何返回或保存结果；
* 哪些地方存在异常处理、判断或分支。

### 第二步：将代码事实抽象为论文概念

例如：

```text
接口参数校验
→ 输入数据有效性检查

build_prompt()
→ 模型输入信息构建

OpenAIClient / ModelClient
→ 模型调用模块

SQL 查询
→ 数据持久化读取过程

save_result()
→ 处理结果持久化

try/catch
→ 异常处理机制
```

### 第三步：重新组织成论文叙事

论文叙事应当遵循：

```text
为什么需要这一流程
↓
整体流程是什么
↓
输入信息是什么
↓
系统如何处理
↓
为什么要经过这些步骤
↓
核心处理如何完成
↓
数据如何继续流转
↓
输出结果是什么
↓
这种设计如何保证功能完整性
```

不要直接按照源码目录顺序写论文。

```text

↓

↓
```

## X.X.3 核心处理过程

这一部分作为重点内容。

请特别强调“因果关系”。

不要只写：

> 由于原始输入无法直接满足模型的输入要求，因此系统首先对请求数据进行结构化整理，并结合当前任务信息构造模型输入。完成输入构造后，系统再将处理后的数据提交至模型服务进行计算，从而保证模型能够按照预期任务完成后续处理。

* 最终形成什么结果；

重点写清楚：

**“原始计算结果”到“最终系统输出”之间发生了什么。**

# 七、强调“为什么”，而不仅仅是“做了什么”

论文正文不能只是流水账。

对于重要步骤，应尽量体现：

```text
为什么需要这一步
→ 这一步具体做什么
→ 产生什么结果
→ 为什么结果可以进入下一步
```

例如，代码事实是：

```text
获取用户输入
↓
清洗文本
↓
构造 prompt
↓
调用模型
```

不要只写：

> 系统首先获取用户输入，然后清洗文本，随后构造提示词，并调用模型。

这种表述信息量过低。

应该改写为：

> 系统接收到用户输入后，需要首先对原始文本进行整理，以减少无效字符或不规范输入对后续处理过程的影响。在完成基础处理后，系统结合当前任务目标对输入内容进行重新组织，使其满足模型调用阶段的数据格式要求。在此基础上，整理后的输入被提交至模型服务，由模型完成相应的内容分析与生成任务。

# 八、保持严格的逻辑链

全文必须保证：

```text
A 发生
↓
因此需要 B
↓
B 得到结果 C
↓
C 成为 D 的输入
↓
D 最终产生 E
```

不要出现逻辑跳跃。

例如：

如果论文写：

> 系统对用户输入进行处理，随后将结果保存至数据库。

那么必须明确：

* 处理得到的是什么结果；
* 为什么需要保存；
* 保存的是哪些信息；
* 保存完成后这些数据在后续流程中有什么作用。

不能突然从“用户输入”跳到“数据库存储”。

# 九、代码细节应该如何处理

代码只能作为论文内容的依据，而不是论文主体。

正文中：

### 可以出现

* 核心模块名称；
* 关键算法名称；
* 必要的数据结构名称；
* 第三方模型名称；
* 数据库名称；
* 必须解释的关键接口；
* 对理解核心机制非常重要的函数。

### 尽量不要出现

* 大量函数名；
* 大量类名；
* 完整文件路径；
* 变量名；
* 参数名；
* 每一个中间方法；
* import 关系；
* 框架样板代码；
* getter/setter；
* 日志代码；
* 与论文研究内容无关的工具函数。

如果某个代码实现细节确实对理解流程非常关键，可以采用：

> 在具体实现中，系统通过相应的数据处理模块完成上述过程。

而不是大段描述代码。

# 十四、避免“AI 味”

# 十五、如果代码与论文抽象层级存在冲突

如果代码非常具体，例如：

```text
request.get("content")
↓
strip()
↓
json.dumps()
↓
client.chat.completions.create()
```

论文不要照搬这些操作。

应抽象为：

> 系统首先获取用户提交的文本内容，并完成必要的格式整理。在输入满足处理要求后，系统按照模型接口所要求的数据结构构造请求内容，随后提交至模型服务完成推理。

但是：

**抽象不能改变实际逻辑。**

如果代码没有文本清洗，就不要写“系统进行了文本清洗”。

如果代码没有权限校验，就不要写“系统首先验证用户权限”。

如果代码没有数据库，就不要自行加入数据库。

# 十八、推荐的段落组织方式

对于每个核心流程，优先使用以下逻辑：

解释这个流程解决什么问题。

### 第二段：整体过程

说明数据从进入系统到产生结果的主要路径。

### 第三段：关键处理

解释最核心的处理机制。

### 第四段：数据流转

解释前后模块之间如何传递信息。

### 第五段：结果输出

解释结果如何形成、处理、保存或返回。

必要时再增加异常处理或分支流程。

不要为了凑段落数量强行拆分。

# 二十二、最终写作标准

请始终记住：

我要的不是：

**“代码执行过程说明书”**

而是：

**“建立在真实代码实现基础上的硕士学位论文章节”。**

读者阅读这一章节时，应当能够理解：

* 为什么系统要设计这套流程；

* 输入数据如何逐步转化为最终结果；
* 各环节之间为什么能够形成完整的逻辑链；
* 具体实现如何支撑论文前文提出的系统设计。

但读者不需要阅读大量源码，也不应该感觉自己正在阅读开发文档。

请以此标准完成全文。
