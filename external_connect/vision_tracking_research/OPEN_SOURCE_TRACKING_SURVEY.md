## Norfair and detector limitations

Norfair provides configurable association and track life cycles; uncertainty admission must still be supplied by the application. `period` is not arbitrary physical `dt`: the inspected tracker calls `tracker_step()` once per update. The adapter advances missing frame steps explicitly and computes velocities from actual replay PTS. It disables appearance ReID rather than promise stable IDs through indistinguishable overlaps. A scalar custom distance can add area/shape/appearance gates but incurs Python pairwise cost; the test uses the existing vectorized Euclidean distance plus conservative ambiguity rejection for control output. Mature tracking is reused, not rewritten. [Tracker API](https://tryolabs.github.io/norfair/2.2/reference/tracker/), [actual 2.3 source](https://github.com/tryolabs/norfair/blob/e517b4236f6b67a6ecf342f5df1fccb7788dbc54/norfair/tracker.py).

OpenCV local background subtraction/thresholding + connected components are cheap and inspectable. SimpleBlobDetector checks persistence across thresholds but its centroids/sizes are still image features, not proof of single bubbles. LoG/DoG and ring detection remain detector options; this task runs the two standard candidates without inventing or training a new network. Severe defocus and overlapping dark features require abstention or labeled segmentation data. [OpenCV SimpleBlobDetector](https://docs.opencv.org/4.x/d0/d7a/classcv_1_1SimpleBlobDetector.html), [connected components](https://docs.opencv.org/4.x/d3/dc0/group__imgproc__shape.html).

## Bonsai feasibility and compatibility

The inspected `CameraCapture` wraps a camera index; `FileCapture.FileName` passes a string to `Capture.CreateFileCapture`. Whether a Chronos RTSP URI works depends on the deployed native backend, not merely the property being a string. The existing Chronos relay workaround is absent from a generic Bonsai source. Prefer retaining the working receiver and bridging compact states, or verify the exact RTSP transport/backend in an independent Windows workflow before replacing anything. [Bonsai source](https://github.com/bonsai-rx/bonsai/tree/ba3abbcb07d7f64aff63aca613587a71858bd806/Bonsai.Vision), [installation](https://bonsai-rx.org/docs/articles/installation.html).

A minimal **DESIGN / NOT_RUN** graph is `frame source → Crop → Grayscale → Threshold → FindContours → BinaryRegionAnalysis → timestamp/quality → ZeroMQ`, with a separate recording branch. Existing Bonsai optical-flow operators were inspected. `Sample` can sample recent events, but adding an unbounded `ObserveOn` queue elsewhere can still accumulate latency. Timestamp at receiver entry, use a bounded latest-frame bridge, measure age downstream and reject old observations. The official closed-loop tutorial demonstrates measurement methods; its Arduino/actuator examples were **not executed**. [Closed-loop tutorial](https://bonsai-rx.org/docs/tutorials/closed-loop.html), [Sample source](https://github.com/bonsai-rx/bonsai/blob/ba3abbcb07d7f64aff63aca613587a71858bd806/Bonsai.Core/Reactive/Sample.cs).

Bonsai.ZeroMQ provides publish/subscribe and other socket integrations. Use compact JSON states with session IDs, units, timestamps and stale flags across Windows/WSL; raw frames need an agreed width/height/stride/pixel-format protocol. The measured local Python ZeroMQ loopback is **not** a Bonsai or cross-OS benchmark. [ZeroMQ documentation](https://bonsai-rx.org/zeromq/).

## CoTracker3 Online: why window timing matters

Pinned `CoTrackerOnlinePredictor` has `window_len=16`, `step=8`, resizes to the model's interpolation shape, and exposes visibility after confidence multiplication and a 0.6 threshold. This visibility flag is not a bubble identity classifier. Initial query points are retained; generic automatic births/re-identification of newly entering bubbles are not provided by the basic online API. Periodic reinitialization needs explicit ID/session handling. `online_demo.py` eventually stores the video for visualization; the bounded test here does not copy that whole-video storage behavior. [Predictor source](https://github.com/facebookresearch/co-tracker/blob/82e02e8029753ad4ef13cf06be7f4fc5facdda4d/cotracker/predictor.py), [online demo](https://github.com/facebookresearch/co-tracker/blob/82e02e8029753ad4ef13cf06be7f4fc5facdda4d/online_demo.py).

At the observed 33.3 ms cadence, 16 frames span 499.5 ms and 8-frame updates are nominally 266.4 ms apart before inference. This is the standard tested scheduling policy, not a claim that every imaginable modified model requires exactly that delay. A history-window tracker may use later observed frames to refine earlier timestamps; only newest available estimates are candidates for current feedback, and age still must be measured. Point tracking can help textured rotation, but cannot resolve absent image information or independently segment a blurred microbubble group.

## DeepLabCut-Live and btrack

Current DLC-Live supports PyTorch exports from DLC3 as well as TensorFlow. The docs identify model-type selection and NumPy inputs; model export/training is a prerequisite. Many identical near-featureless spheres differ from a small named landmark set on a structured animal. No task-specific detector weights were available, so no misleading pose speed test on an unrelated model was run. [Current README](https://github.com/DeepLabCut/DeepLabCut-live/blob/e61f726731825993933b0cd43e27ce019741a618/README.md).

btrack local Bayesian association and global tracklet optimization solve different problems. Incremental Python methods exist but deployment still needs evidence for active-stream append/step behavior, bounded memory and output deadlines. Global optimization can revise identities using future observations and is unsuitable as evidence of online control accuracy. [API source](https://github.com/quantumjot/btrack/blob/2de42c911253e021b3814191fd1a049a6c0e2628/btrack/core.py), [user guide](https://btrack.readthedocs.io/en/latest/user_guide/index.html).

## Flow and buffering

LK tracks sparse textured points; the test uses current↔previous consistency checks, which do not read future frames. Farnebäck estimates dense image motion and costs more at broad ROI. Both can respond to fixed texture, defocus, illumination and projection changes. Their output is **image motion in px per replay second**, not fluid velocity or ultrasound causality. [OpenCV flow documentation](https://docs.opencv.org/4.x/d4/dee/tutorial_optical_flow.html).

For GStreamer before 1.28 a typical endpoint is `appsink max-buffers=1 drop=true sync=false`; in 1.28+ use `max-buffers=1 leaky-type=downstream sync=false`, after inspecting installed properties with `gst-inspect-1.0 appsink`. `sync=false` disables sink clock waiting; it does not remove upstream buffering. `rtspsrc` jitter latency and drop-on-latency, decoder reordering and upstream queues need separate validation. These are **configuration guidance, NOT_RUN**, and should not replace the verified Chronos FFmpeg settings without live measurements. [appsink](https://gstreamer.freedesktop.org/documentation/app/appsink.html), [rtspsrc](https://gstreamer.freedesktop.org/documentation/rtsp/rtspsrc.html).

Chronos official network guidance covers preview/API access; preview rate, high-speed recording rate and software consumer rate are different. The existing project and recorded files, not a generic advertised FPS, determine this task's measurements. [Chronos examples](https://github.com/krontech/chronos-examples), [Krontech network guide](https://support.krontech.ca/en/articles/8814068-network-control-of-chronos-high-speed-cameras-via-webpage-live-video-stream-and-rest-api).
